# Discussion command API

`GET /api/discussion` returns the authenticated member's current discussion state and its storage revision. `POST /api/discussion` accepts one strict command with a caller-generated `message_id` UUID and `confirmed: true`. The authenticated member token supplies the actor and shared-space scope; request fields cannot select either identity.

Commands create a topic, propose an exact consensus/settlement/reopen/switch action, or approve the stored proposal. A proposal does not count as an approval. Each member must submit a distinct confirmed approval whose text exactly matches the original proposal, including whitespace. A confirmed consensus adds a per-topic agreement and leaves the topic active. A confirmed principle adds an agreement with `thread_id: null`, increments the shared principle revision, and leaves its source topic active. Settlement records the exact conclusion in topic history; reopening preserves that conclusion while returning the topic to pending. Switching writes both topic status versions at the same command event.

Every command is accepted through a single database batch that updates the compact current projection, appends an immutable `discussion_command` event, and appends affected topic and agreement versions. A lost compare-and-set returns `storage_conflict`; retry the identical action with the same `message_id`. The receipt reports the original persisted event for an identical retry. Reusing a UUID with different text, action, space, or actor returns `command_conflict` without returning the original content. `GET /api/discussion/{message_id}` only returns a receipt submitted by the currently authenticated member; other members' UUIDs and nonexistent UUIDs both return `receipt_not_found`.

The compact projection has a 1 MiB serialized limit, below D1's 2 MB row/string limit with room for database overhead. A command body remains limited to 64 KiB. When the projection reaches its finite budget, new commands fail explicitly and no history is removed; there is no automatic cleanup. If actual use approaches this cap, move retained command details into relational history and keep only a compact current projection. Existing thread history without a projection returns `projection_uninitialized`; reads and writes do not reconstruct partial state or silently initialize over that history. Membership is checked before work and again in the SQL-guarded write. Reads also fail closed when the projection violates core state invariants such as a single active topic, bilateral approvals on applied proposals, or agreement-to-proposal binding.

The `confirmed` field records the caller's assertion; it is not server proof that a human reviewed the text. Persisting a command or queued expression does not execute a therapist, model, cloud job, invitation, or automated action. No worker or provider result is claimed by this API.

# Confirmed expression intake

The Sites API accepts an authenticated member's confirmed expression for the latest active thread. `POST /api/messages` accepts only `message_id`, `thread_id`, `expected_thread_seq`, `text`, and literal `confirmed: true`. The actor and shared space come from the signed-in member context. Extra properties, invalid UUIDs, blank text, stale thread versions, non-active threads, missing membership, non-JSON bodies, invalid UTF-8, and bodies larger than 64 KiB are rejected.

The submitted text is stored exactly as provided, including leading or trailing spaces and paragraph breaks. The confirmation flag records the caller's assertion; this API cannot prove that a person saw or approved the exact text. The local Therapist Assistant must show the exact outgoing text and obtain confirmation before it calls this endpoint.

The HTTP routes bind the Agent member through the pre-generated Bearer token and its current D1 membership. The browser read-only view uses a separate HttpOnly session cookie established from the same token. Hosting-platform visitor identity headers and request JSON do not choose the actor or space.

The service writes one immutable `member_expression` message and one `therapist_tasks` row with `status = 'queued'` and the verified `expected_thread_seq` in one D1 batch. The SQL checks current membership and the latest active thread version during insertion. A repeated identical UUID and payload returns the original receipt; reusing the UUID for different text, actor, space, or thread returns a conflict. A receipt includes the server sequence and creation timestamp, exact text, and the current `task_status` (`queued`, `running`, `failed`, `obsolete`, or `completed`). The original message identity, text, and time do not change as that status changes.

`GET /api/messages/{messageId}` returns a receipt only for an expression submitted by the authenticated member in the member's current space. Missing and out-of-scope messages both return not found.

**A queued receipt proves persistence and queue acceptance only.** The service now has a manually triggered durable worker with fenced leases, persisted orchestration checkpoints, strict source citations, and atomic reply publication. `POST /api/therapist/drain` processes at most one task using server-side configuration. Task completion is visible through the member view and receipt; a completed automatic understanding or proposal does not count as either member's acceptance. No unattended trigger is installed, and injected-provider SQLite verification does not prove a real provider call or hosted execution. See [`therapist-worker.md`](therapist-worker.md).

Migration `0005_magical_goblin_queen.sql` rebuilds the task table to add captured thread-version metadata while preserving each historical task status; historical rows receive `input_thread_seq=0`. The worker explicitly marks such rows obsolete at runtime because they have no verified `expected_thread_seq`; it does not silently assign the current thread version. Migration `0006_marvelous_skreet.sql` adds bounded retry metadata and output completion fencing while retaining all existing task columns. These migrations have not been applied to a hosted database, and this implementation does not enroll members, seed relationship data, make a real provider call, or install an automation.

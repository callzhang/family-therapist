# Therapist output contract

The provider response has six required fields: a natural shared `reply`, cited `source_message_ids`, `common_points`, `differences`, `hypotheses`, and a nullable `consensus_proposal`. Each list item contains only `text` and `source_message_ids`. Provider schema strictness rejects unknown keys, including action fields such as settlement, approval, or actor overrides. Strings and lists are bounded; proposal is represented as either a cited item or `null`.

`validateTherapistOutput(output, context)` is the application eligibility gate. Its context must be assembled by the server for the frozen run snapshot and contains the space, thread, snapshot sequence, two distinct member IDs, and message metadata. Space and member IDs are opaque stable identities and need only be nonblank; exact values are preserved and compared. Thread IDs and cited message IDs must be UUIDs. Every cited ID must resolve uniquely to a persisted (`seq > 0`) member's formal `member_expression` in that scope and at or before the snapshot. Each automatic common point and each non-null consensus proposal requires cited expressions from both distinct members. A reply from one member is valid with an empty `common_points` list and a null proposal.

Successful validation returns a frozen clone; it does not mutate provider output. A proposal remains a proposal and validation never approves it, creates an agreement, settles a thread, or changes status. Citation eligibility proves only that a reference exists in the permitted evidence set. It does not prove that the cited wording semantically supports the generated reply or summary, establish clinical quality, or certify a consensus. Those claims require separate human review and behavioral evaluation.

Provider completion/parsing and application validation are separate states. The Responses transport loop currently reports a parsed completed output; until the application commit boundary invokes this validator, that status alone does not mean the output passed these checks or became durable. This module does not alter provider transport, persistence, recovery, or the hosted generation pipeline. Durable integration must call validation on server-supplied snapshot metadata before committing output and must preserve the validation result as a distinct gate.

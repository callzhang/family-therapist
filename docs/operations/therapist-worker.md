# Durable Therapist worker

`POST /api/therapist/drain` manually asks the service to process at most one accepted expression in the authenticated member's current space. The request has no body. The member identity and space come from that member's Bearer token; model, instructions, schema, and tool budget come from server configuration. After authentication and configuration checks, it returns a private, no-store NDJSON stream with `started`, periodic `keepalive`, and one terminal `result` or safe `error` frame. HTTP 200 means only that the stream was established. A terminal `result` with task status `completed` means the service transactionally stored one validated Therapist reply and one automatic understanding record; it does not mean either member accepted a proposal. Other worker statuses such as `idle`, `failed`, or `obsolete` are not success.

`POST /api/therapist/retry/{messageId}` is an explicit authenticated retry for a failed transient or quota-limited task. It preserves the task's frozen model/configuration and saved checkpoint, and permits at most three retries. Eligibility is checked before the stream is opened. A 429 or exhausted-credit response is never retried automatically; restore provider capacity, then invoke this endpoint deliberately. Its established stream uses the same NDJSON terminal result contract as `drain`.

The worker leases one task per thread. It pins the original active-thread version, current two-member registry, confirmed global principles, bounded server configuration, and the message snapshot before calling the provider. Read tools use that frozen snapshot. The final validated `source_message_ids` must include the expression that triggered the task; only other queued expressions explicitly named in that same source list can be marked covered. A task whose expression is omitted fails as `invalid_output`, and unreferenced queued expressions remain queued for their own turn. Checkpoints are capped at 1 MB; oversized orchestration state fails closed rather than being truncated. A takeover first checks current thread/member/principle state before any resumed provider request, and can resume a valid checkpoint under the same run identity; the previous lease owner cannot save or publish. Before publication, the worker repeats those checks inside the guarded completion statement. A unique completion lease marker fences each output insert and coverage update in the same D1 batch. UUID collision or any failed guard aborts and rolls back the entire batch. Inputs created after a frozen snapshot remain queued for another run.

Migration `0005_magical_goblin_queen.sql` preserves every task's status and assigns `input_thread_seq=0` to historical tasks without a captured version. Runtime explicitly marks those records obsolete instead of inventing a source version. Migration `0006_marvelous_skreet.sql` adds completion fencing and bounded retry metadata while preserving all existing task data.

A process can stop after the provider has generated a response but before D1 stores that response checkpoint. Recovery may then repeat a provider request and its billing. Stable task UUIDs and the final D1 transaction prevent duplicate public business records; they cannot guarantee exactly-once provider billing.

Set `THERAPIST_API_BASE_URL` to the trusted HTTPS Responses API base URL (for example, a provider's `/v1` endpoint), `THERAPIST_MODEL` to the selected model, and `THERAPIST_API_KEY` through the hosting provider's server-side secret store. The adapter uses manual redirect handling and rejects every 3xx response before reading its body, bounds response size and each provider call to 90 seconds, and sends `FamilyTherapist/1.0`. A canceled stream aborts an active provider call; the request wrapper checks cancellation before starting each subsequent call. The worker uses medium reasoning and an 8192-token output budget. Neither endpoint nor credential is stored in task configuration or checkpoints. Do not put these settings in request JSON, source control, browser storage, or a shared member token.

`skills/cloud-therapist/SKILL.md` and its consultation-method reference are bundled into the server instructions. Bump `CLOUD_THERAPIST_SKILL_VERSION` when those instructions change so each run records the version it used. The final generation phase runs without tools and requests the strict output schema after evidence queries complete.

`GET /api/view` includes the latest task state for the selected thread. The member page translates `queued`, `running`, `failed`, `obsolete`, and `completed` into explicit status text. Receipts continue to preserve the original expression, UUID, and creation time while returning the current task status.

This worker has an explicit manual trigger. No scheduled or unattended trigger is installed by this change. Local isolated-SQLite QA has exercised actual configured provider Responses tool calls and final generation through `runNextTherapistTask`, including transactional reply/understanding publication and queued-item coverage. Hosted API settings, production D1 migration, a hosted request, and the browser-visible result remain separate deployment checks.

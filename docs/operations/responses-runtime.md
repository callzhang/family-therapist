# Therapist Responses runtime contract

`packages/therapist/tools.mjs` exports the finite read-only function protocol. Its five function definitions set `strict: false` because list filters, cursors, and page limits are optional. Those nullable properties declare `default: null`; the local validator checks only supplied values, fills omitted optional values with `null`, and returns canonical arguments to every executor. Required thread and message UUIDs remain required. Function schemas reject additional properties, and the validator independently rejects every extra property, including actor, space, snapshot, and prototype-key fields. Tool arguments never choose identity, space, scope, or snapshot; the authenticated server scope is a separate argument and the query adapters enforce membership and snapshot bounds from it. Final therapist output continues to use its separate strict JSON Schema.

`runTherapistTurn` accepts `model`, `instructions`, `input`, an authenticated `scope` containing `run_id`, `actor_id`, `space_id`, and `snapshot_seq`, `maxToolCalls`, an application-provided `outputSchema`, an injected Responses-compatible `request`, an injected `executeTool`, and awaited `saveCheckpoint`. It first uses the read-only tools without a structured-output constraint. After evidence gathering stops, it checkpoints a distinct final-generation phase and makes a no-tools request with the strict JSON Schema, continuing from the preceding provider response ID. That final request explicitly includes the frozen original input and the persisted tool results, so final generation never depends on an empty continuation input or implicit provider history. Only text in the last assistant-role message is parsed; reasoning and non-assistant content are excluded.

The server adapter uses `redirect: "manual"` and rejects every 3xx response before reading its body. This avoids unsupported redirect modes in the deployed Workerd runtime while ensuring provider credentials are never forwarded to a redirect destination. The request-construction and redirect behavior are covered in the pinned Miniflare/Workerd compatibility runtime as well as the adapter unit tests.

A checkpoint retains the original input, all four authenticated scope fields (`run_id`, `actor_id`, `space_id`, and `snapshot_seq`), the model, most recent provider response ID and status, processing phase, raw most recent provider response, pending function calls, cached tool results, and, after completion, the parsed output. Recovery requires the supplied scope and model to match the checkpoint. The application persists each provider response and each individual tool result before continuation. Evidence responses and final responses are stored in separate processing phases before parsing, so recovery can process saved responses without repeating those requests. A completed checkpoint returns its cached output without a provider call. Tool-result identities are `${run_id}:${call_id}`. On recovery, cached result records are reused; a read may be repeated if a process stopped after executor completion but before its result checkpoint was committed. The query executor receives the identity key so its audit layer can correlate retries.

The return value is `{ status: "completed", output, checkpoint }` only after a completed provider response with parseable JSON and no pending calls. Provider, argument, executor, parse, budget, or checkpoint errors return an explicit failed result with the latest usable checkpoint attached to both the error and result. A provider response that reuses a previously executed function-call ID fails explicitly; a saved `tools_pending` checkpoint may still reuse its already-persisted result during resume. No final reply is synthesized for a failed or incomplete run. Application code remains responsible for validating output references, persisting the final business result, and scheduling/resuming durable work.

Automated tests cover optional tool arguments and checkpoint recovery. Local tests do not establish hosted scheduling, a production deployment, or clinical effectiveness; validate each independently in the deployment environment.

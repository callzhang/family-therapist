# Therapist Responses runtime contract

`packages/therapist/tools.mjs` exports the finite read-only function protocol. Its five strict JSON Schema definitions are the complete model-visible tool set. Optional query fields are required by strict mode and represented as nullable values. The executor validates arguments against own schema properties and rejects every extra property, including actor, space, snapshot, and prototype-key fields. It receives the authenticated server scope as a separate argument. Query adapters must enforce membership and snapshot bounds from that scope; this module does not authenticate or access a database.

`runTherapistTurn` accepts `model`, `instructions`, `input`, an authenticated `scope` containing `run_id`, `actor_id`, `space_id`, and `snapshot_seq`, `maxToolCalls`, an application-provided `outputSchema`, an injected Responses-compatible `request`, an injected `executeTool`, and awaited `saveCheckpoint`. The model and instructions are sent on every request. Each continuation sends function outputs with the matching `call_id` and references the preceding provider response ID. Structured output is requested in strict JSON Schema mode.

A checkpoint retains the original input, all four authenticated scope fields (`run_id`, `actor_id`, `space_id`, and `snapshot_seq`), the model, most recent provider response ID and status, processing phase, raw most recent provider response, pending function calls, cached tool results, and, after completion, the parsed output. Recovery requires the supplied scope and model to match the checkpoint. The application persists each provider response and each individual tool result before continuation. A response is stored in a non-completed processing phase before it is parsed or any returned tool is run, so recovery can process that response without making another provider request. A completed checkpoint returns its cached output without a provider call. Tool-result identities are `${run_id}:${call_id}`. On recovery, cached result records are reused; a read may be repeated if a process stopped after executor completion but before its result checkpoint was committed. The query executor receives the identity key so its audit layer can correlate retries.

The return value is `{ status: "completed", output, checkpoint }` only after a completed provider response with parseable JSON and no pending calls. Provider, argument, executor, parse, budget, or checkpoint errors return an explicit failed result with the latest usable checkpoint attached to both the error and result. No final reply is synthesized for a failed or incomplete run. Application code remains responsible for validating output references, persisting the final business result, and scheduling/resuming durable work.

Verification recorded for this implementation: `node --test tests/therapist/responses.test.mjs` passed 23 tests; `node --test tests/protocol/*.test.mjs` passed 15 tests. These checks cover deterministic orchestration and checkpoint contracts only. They do not demonstrate live provider access, durable hosted scheduling, authentication enforcement in an adapter, consultation quality, or clinical effectiveness.
